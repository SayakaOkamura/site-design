## いまの形

```
一 書く    白紙に一行。例を4つ並べ、空 Enter でいちばん上が入る
             ↓
二 決める  空の画面に、決まったことが斜めの一筆でまとめて現れる
           （1.7秒／26ステップ。刻んで進めると「書いている」に見える）。
           決まっている＝文字がある／決まっていない＝線だけ。入力欄の枠は出さない。
           操作はゼロ。押すのは「稟議に上げる」だけ
             ↓
三 通す    起案 ● 確認 ● は通るのに、決裁で止まる。
           AI が画面を見直し、決まっていない欄を3つ見つける。
           「N 件を決める」の一手で、空欄が順に書き込まれる（段2と同じ書き味）。
           決裁が下り、完了通知に
           「出したときは決まっていなかった N 件を、通す前に決めました」が残る
```

操作は **書く1・稟議に上げる1・決める1 の計3回**。全部が判断のある操作。

## 判断の指針（今日決めたこと）

1. **判断のない操作は置かない。**答えが一つしかない選択も置かない（偽の選択）
2. **決めるのは人、見つけるのは AI。**見つけたのが AI だと画面上で分かるようにする
3. **出すのは言葉ではなく物。**穴も、言葉のカードではなく物の上の空欄として見せる
4. **「これで通せる」と思わせてから外す。**漏れは段2では出さない
5. **咎める書き方をしない。**評価も価値の説明も置かず、事実と次の一手だけ
6. **段の名前と中身が食い違ったら、中身を直す。**名前を content に寄せるのは逃げ

## 却下された方向（繰り返さない）

003 からの継続分。

| 案 | 却下の理由 |

005 で新たに却下したもの。

| 案 | 却下の理由 |
| --- | --- |
| 付箋を3ゾーン（決めた／未定／やらない）に振り分ける | 書いたことまで振り分けさせるのは無駄。決まっているものを動かす意味がない |
| 判子を人が3回押す（起案・確認・決裁） | 押すしかない操作。判断が入らない |
| 「戻って直す」を稟議に置く | 判子が押された紙は戻せない。矛盾 |
| 空欄を1枚ずつカード送りで出す | 捌かされている感じになる。全部見えているほうがいい |
| きまりを「入れるか入れないか」選ばせる | 答えが一つしかない偽の選択 |
| 段2 を「出る」に改名して名前を中身に合わせる | 逃げ。中身のほうを直す |
| 空欄に付箋を貼る（現在の作りで） | 紙に貼って見えず、ただの色つきラベルだった。**やるなら罫線をまたいで重なり、傾き、影が落ちる作りにする** |
| 完了通知に所要秒数を出す | 速さの話は「決めていないところ」とぶつかる |
| 講釈（「それがこの順序の値打ちです」） | 説教になる。事実だけ置く |
| 決まった値を入力欄の枠に入れて見せる | 触れないものを触れるように見せるのは嘘。決まっている＝文字がある、決まっていない＝線だけ |
| 押せない「申請する」ボタンを画面に置く | 同上。押せないものをボタンの形で見せない |
| 元になった語が光ってから部品が入る演出 | 対応関係の説明になっていた。書き上がりの勢いを削ぐ |
| 空欄を1件ずつ矢印で決めさせる | 「N 件を決める」の一手に集約。送りは操作であって判断ではない |
| ボタンを画面の外（下）に置く | 外にあると押すものに見えない。空欄のすぐ下、画面の中に置く |
| 「こちらで埋めました」と書く | 主語がこちらに寄る。決めたのは人という建て付けと食い違う |

## 未解決・次にやること候補

1. **見出しが未決。**いまは「決めていないことを、作る前に見つける。」。
   他の候補：作ってから気づくものを、決める前に出す／決めていないところが、いちばん高くつく
2. **書き上がりに約2.3秒（420 の待ち＋1700 の一筆＋150）。**プレゼンでは見せ場だが、
   2回目以降は待ち時間。早送りを入れるか。速度は `script.js` の
   `setTimeout(… 'sweep' …, 420)` と続く `420 + 1700 + 150`、
   CSS の `#rules.sweep`（`chalk 1.7s steps(26, end)`）。**変えるときは3箇所を揃えること**
   （`style.css` に `#rules.sweep` は2行ある。後ろの 1.7s が効いている）
3. **自由入力が語彙頼み。**10件試して素直に拾えたのは3件。
   外れると「この業務の画面」に落ちる。**実運用するなら API 化が要る**（下記）
4. **API 化は GitHub Pages では不可。**ブラウザにキーは置けないので自前のエンドポイントが要る。
   `extract()` 一箇所の差し替えで済むようにはしてある。置き場所（Cloudflare Workers 等）とモデルは未決。
   レート制限と入力文字数の上限は必須
5. **語彙の粗さ。**「顧客管理」で「顧客名」と「会社名」が両方出る。
   対象語の誤爆もある（「社内の備品を貸し出して」→ 対象語が「社内」になる）
6. **ロゴが未着。**実ロゴが来たら差し替える（現在は文字のみ）
7. 縦がぎりぎり。**何か足すときは、同時に何を削るかを決めること**

## 運用メモ

- **CSS/JS は `?v=N` 付き。中身を変えたら番号を上げる。**
  GitHub Pages は Cache-Control を設定できないため、上げないと古い版が出る
- ローカル確認は静的サーバが必要（`file://` では動かない。Chrome 拡張からも開けない）
- 高さの調整は**表示領域 631px** で詰めてある。実機ではもっと余裕がある
- **ワンライナーでのファイル編集はしないこと。**この設計中に2回壊した。
  - `perl -0pi -e` の中で `local(@ARGV,...)` を使い、`script.js` が 0 バイトになった。
    `node --check` は空ファイルを通すので気づけない
  - bash のダブルクォート内に `$('...')` を書き、シェルがコマンド置換して
    `sed` の正規表現が空になり、`.onclick` を含む行が全部消えた
- 004 のスケッチは残置。B（正解のない問い）C（現場↔経営）F（偽LPで落とす）は
  005 に採らなかったが、別方向として生きている
